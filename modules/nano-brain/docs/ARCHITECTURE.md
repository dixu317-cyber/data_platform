# Nano GBrain 架构骨架

版本：v0.1
状态：草案
核心原则：用户体系独立于具体知识库链路。管理员只有一个层级，并拥有所有知识库链路的完整管理权限。Nano Brain 只是其中一条知识库链路，不拥有全局用户模型。

---

## 1. 架构定位

系统不是单一知识库产品，而是一个可承载多条知识库链路的平台。

示例：

```txt
同一个用户 Bob
  → 传统 RAG 知识库
  → GraphRAG 知识库
  → Nano Brain 知识库
```

三条链路共享：

- 用户身份。
- 用户是否为管理员。

三条链路不共享：

- 原始文档。
- 上传链路。
- 处理链路。
- 检索链路。
- 维护链路。
- 链路内部权限模型。

---

## 2. 总体分层

```txt
身份层
  → 用户、登录、管理员身份

知识库链路注册层
  → 注册不同知识库链路
  → 暴露统一入口，但不统一内部实现

链路适配层
  → 传统 RAG 适配器
  → GraphRAG 适配器
  → Nano Brain 适配器

链路内部核心层
  → 各自的上传、处理、检索、维护、权限

存储层
  → 用户库
  → 传统 RAG 数据库
  → GraphRAG 数据库
  → Nano Brain 数据库
```

---

## 3. 身份层

身份层只负责回答两个问题：

```txt
这个人是谁？
这个人是否是管理员？
```

身份层不负责普通用户在各链路内的细粒度权限判断，例如能否读取某个 Nano Brain source、能否使用某个传统 RAG collection。

但管理员身份是全局有效的：管理员拥有所有知识库链路的完整管理权限。各链路必须识别管理员身份，并允许管理员执行该链路内的全部管理操作。

### 3.1 用户模型

概念模型：

```txt
用户
  - 用户标识
  - 邮箱
  - 名称
  - 是否管理员
  - 创建时间
```

管理员是唯一管理层级。管理员拥有进入管理端、管理用户、管理所有知识库链路以及执行各链路内全部管理操作的权限。系统不再设计链路管理员、局部管理员或多级管理员。

---

## 4. 知识库链路

知识库链路是相互隔离的业务系统。

每条链路必须独立拥有：

- 上传入口。
- 原始文档存储。
- 处理管线。
- 检索方法。
- 维护任务。
- 内部权限模型。
- 审计记录。

### 4.1 传统 RAG 链路

面向普通文档检索问答。

典型能力：

```txt
文档上传
  → 文档解析
  → chunk
  → embedding
  → 向量检索
  → 问答
```

### 4.2 GraphRAG 链路

面向实体、关系、社区摘要和图谱推理。

典型能力：

```txt
文档上传
  → 实体抽取
  → 关系抽取
  → 图谱构建
  → 社区摘要
  → 图谱增强检索
```

### 4.3 Nano Brain 链路

面向个人和公共 source 的轻量知识脑。

典型能力：

```txt
Markdown 页面
  → page pipeline
  → chunk
  → embedding
  → links
  → facts
  → dream
  → 检索与问答
```

---

## 5. 统一入口与链路隔离

系统可以提供统一入口，但入口只做分发，不做业务融合。

```txt
HTTP API / MCP Server
  → 识别目标链路
  → 调用对应链路适配器
  → 适配器调用链路内部核心能力
```

禁止：

```txt
统一入口直接操作某条链路数据库
统一入口绕过链路内部权限
统一入口把三条链路的检索结果强行混合
```

允许：

```txt
统一列出当前用户可访问的知识库链路
统一进入某条链路的管理页面
统一展示任务状态
统一展示任务状态
```

---

## 6. 链路适配器契约

每条知识库链路对外暴露一组最小能力，而不是暴露内部实现。

建议契约：

```txt
获取链路信息
获取当前用户在该链路的权限摘要
上传内容
检索
问答
获取健康状态
执行维护任务
进入管理操作
```

其中“权限摘要”只用于展示，不替代链路内部权限判断。

---

## 7. 管理员模型

系统只有一个管理员层级。管理员身份来自身份层，并在所有知识库链路中全局有效。

管理员拥有：

- 进入管理端。
- 查看和管理系统用户。
- 查看和管理已注册知识库链路。
- 管理传统 RAG 链路中的全部知识库、文档、索引和维护任务。
- 管理 GraphRAG 链路中的全部图谱、文档、索引和维护任务。
- 管理 Nano Brain 链路中的全部私有 source、公共 source、事实审核、知识图谱和 dream 任务。

系统不设计：

- 链路管理员。
- 局部管理员。
- 分级管理员。
- 只管理某一个知识库链路的管理员。

普通用户在不同链路中仍然可以有不同的业务权限，但这些权限不构成管理员层级。

---

## 8. Nano Brain 核心能力边界

Nano Brain 的所有业务能力必须优先实现为模块 core 函数，HTTP API 和 MCP Server 都只是入口适配层。

```txt
modules/nano-brain/src/core
  → HTTP API
  → MCP Server
```

当前 core 目录包括：

```txt
core/sources.ts       # source 管理与权限相关能力
core/pages.ts         # Markdown page pipeline
core/permissions.ts   # Nano Brain 内部权限判断
```

核心能力必须遵守：

1. source 权限判断必须在 core 内完成。
2. Markdown 校验、slug 生成、标题提取、content hash、页面写入必须在 core 内完成。
3. HTTP API 只能做鉴权、参数映射、调用 core、返回 JSON。
4. MCP Server 后续必须直接调用同一套 core 函数，不能通过 HTTP API 转发。
5. 禁止把业务能力只实现于 `apps/api`。
6. 禁止 HTTP API 和 MCP Server 各自实现一套业务逻辑。

示例：

```txt
putMarkdownPage(ctx, input)
  → HTTP API: POST /nano/pages
  → MCP Server: nano_put_page，后续如开放写入工具
```

这样可以确保后期 MCP 接入时直接复用已有能力，而不是被 HTTP API 强绑定。

---

## 9. Nano Brain 在平台中的边界

Nano Brain 只负责自己的知识库链路。

Nano Brain 内部包含：

- 私有 source。
- 公共 source。
- page pipeline。
- 知识图谱。
- 事实提交与审核。
- dream。
- Nano Brain 内部权限。

Nano Brain 不负责：

- 注册用户。
- 登录认证。
- 判断用户是否是管理员。
- 管理传统 RAG 文档。
- 管理 GraphRAG 图谱。

Nano Brain 接收身份层传入的用户上下文：

```txt
用户标识
是否管理员
请求来源
```

然后在 Nano Brain 内部判断：

```txt
是否能读某个 source
是否能写自己的私有 source
是否能管理公共 source
是否能审核事实
是否能执行 dream
```

---

## 10. 存储边界

推荐存储分离：

```txt
用户数据库
传统 RAG 数据库
GraphRAG 数据库
Nano Brain 数据库
```

至少逻辑上必须分离。

禁止把三条链路的原始文档、chunk、图谱、source 混在同一套业务表里。

可以共享：

- 用户标识。
- 全局审计事件。
- 链路注册表。

不共享：

- 文档表。
- chunk 表。
- embedding 表。
- 图谱表。
- source 表。
- 链路内部权限表。

---

## 11. 推荐开发顺序

### 阶段 1：身份骨架

目标：只做最小用户体系。

交付：

- 用户注册。
- 用户登录。
- 管理员标记。
- 当前用户上下文。

### 阶段 2：链路注册骨架

目标：让系统知道有哪些知识库链路。

交付：

- 链路注册表。
- 链路列表。
- 链路适配器接口。
- 空的 Nano Brain 适配器。

### 阶段 3：Nano Brain 纵向闭环

目标：先打通一条真实链路。

交付：

```txt
用户
  → 私有 source
  → Markdown 上传
  → page pipeline
  → chunk
  → embedding
  → 检索
```

### 阶段 4：Nano Brain 管理能力

交付：

- 公共 source。
- 事实提交。
- 管理员审核。
- 知识图谱基础查询。

### 阶段 5：Nano Brain dream

交付：

- dream 执行器。
- 链接重建。
- embedding 补齐。
- 健康报告。

### 阶段 6：接入其他知识库链路

交付：

- 传统 RAG 适配器。
- GraphRAG 适配器。
- 各自独立上传、检索、维护链路。

---

## 12. 核心架构约束

1. 身份层负责用户身份和唯一管理员身份。普通用户的链路业务权限由各链路自行判断。
2. Nano Brain 不能拥有全局用户体系。
3. 每条知识库链路必须拥有独立数据模型和独立处理链路。
4. 统一入口只能分发请求，不能绕过链路核心能力。
5. Nano Brain 第一阶段不提供正式 CLI；HTTP API 和 MCP Server 必须调用同一套 core 能力。
6. Nano Brain 任何业务能力不得只存在于 HTTP API 中。
7. MCP Server 后续必须直接调用 `modules/nano-brain/src/core` 中的能力。
8. 链路内部权限必须由链路自己判断，但管理员必须拥有所有链路的完整管理权限。
9. 系统不设计链路管理员、局部管理员或多级管理员。
10. 第一条链路必须先形成完整闭环，再扩展第二条链路。
